Round 2 — BotW first invalid guest access (2026-10-03)

The patch is in the working tree. No build, emulator run, commit, or push was performed. The existing console logs do not contain a guest PC, so they cannot identify the instruction retrospectively. This patch captures the instruction and its operands on the next reproduction; it does not establish which earlier instruction or input first corrupted them.

The run's first fault is a **Read8**, not a store: `botw-eden-eden.txt:135–136` reports `0x21dda30013`, followed by reads at `...14–16` and byte writes. The address is `0x16a30013` beyond the successfully allocated heap end. It is not a page-crossing access. Around 11 seconds the log mounts DLC content; the first fault is at 13.752895 seconds. That is a correlation, not proof that DLC causes it. The frontend log supplies no CPU accuracy override; its late samples show roughly 4.066 GB process memory and no frames, not a guest PC.

Ranked findings, ordered by usefulness for the next investigation:

1. **Update/mod input integrity remains unverified; the loader had concrete validation holes.** `src/core/loader/nso.cpp:122` now reads an uncompressed segment using its uncompressed size rather than trusting the compressed-size slot. Previously one shared buffer was sized only from compressed-size slots, short reads were ignored, and raw copies could consume stale bytes or exceed that buffer for inconsistent metadata. Decompression now requires the exact output size and returns a loader failure instead of relying on the soft-assert policy. Segment/image arithmetic is widened before addition, the allocation covers all segment ends, argument data is bounded, and a resized patch image is rejected before copying. These are proven malformed-input hazards, **not proof that this BotW update triggers them**.

   Compression bits 0–2 still select text/rodata/data compression; bit 7 still selects ZBIC rather than LZ4. `src/core/loader/nso.cpp:160` observes SHA256 check bits 3–5 and compares each decompressed, unpatched segment with its header hash. Hash comparison is diagnostic, not a new rejection policy: deliberate replacements can have stale hashes. `hash_ok=false` is meaningful as an integrity failure only when `hash_enabled=true` and the hash operation succeeded. The final module digest covers the padded image including BSS, after NSO patches, before runtime relocation; it is not directly comparable to a segment hash.

   `src/core/file_sys/patch_manager.cpp:198` replaces ExeFS with the selected update, then overlays enabled mod directories. `src/core/loader/deconstructed_rom_directory.cpp:173` reloads **the resulting** `main.npdm`; it does not keep the base NPDM. Build-ID matching for IPS/IPSwitch is in `src/core/file_sys/patch_manager.cpp:386`; no UWP-specific segment-offset branch was found. The existing “LayeredExeFS patches applied successfully” message also occurs with only the original ExeFS layer, so it does not prove a mod is active. New `EXEFS_LAYER` lines enumerate candidate replacement files; `nso_patched` reports an actual NSO-image change. First matching layered file wins. `ApplyLayeredFS` at `src/core/file_sys/patch_manager.cpp:543` handles RomFS separately, not executable loading. NSO hashes cannot exonerate corrupted RomFS/DLC or guest decompression of asset data. The displayed `v0.17.0` is a formatted content version, not independent verification of the marketing version “1.6”; `EXEFS_UPDATE` now records the explicitly selected external version when available.

2. **A64 JIT/configuration is still a plausible cause, but no instruction-emulation defect was proven.** `src/core/arm/dynarmic/arm_dynarmic_64.cpp:375` enables unsafe optimizations, unfused FMA and ignore-global-monitor in Auto. The actual frontend in this worktree sets fastmem options off; it does **not** force Accurate (`src/eden_uwp/game_session.cpp:397`). Settings-file overrides are applied afterward. Auto is also an upstream default, so this alone does not explain an Xbox-only failure. `NXBOX FAULT CONFIG` records the actual configuration passed to each JIT, avoiding inference from UI settings. No accuracy, timing, page-table, or exclusive-monitor settings were changed by this patch.

   `always_little_endian` is an A32 option in this tree, not a missing A64 setting. The A64 standard-FPCR-ignore setting is likewise not used by this wrapper; that setting is consumed in the A32 wrapper. A64 context switching transfers FPCR/FPSR, FPCR participates in block identity, and `src/dynarmic/src/dynarmic/backend/x64/a64_jitstate.cpp:60` maps rounding and flush-to-zero to MXCSR. `wall_clock_cntpct` follows multicore mode through `InitializeInterfaces`, and CNTPCT calls the core clock. These paths are shared with desktop; no Xbox-only FPCR/endian/timer override was found.

3. **Exclusive writes retained the contiguous-pointer assumption and could falsely report success. Fixed, with a qualification.** `src/core/memory.cpp:793` refuses misaligned stores before host CAS. Naturally aligned widths of 1/2/4/8/16 bytes cannot cross a 4 KiB page; the guard also protects MSVC's aligned 128-bit CAS. Unmapped exclusive stores now return failure instead of `true`. No split byte writes emulate an atomic store. This is host-memory protection, **not full guest alignment-abort delivery**; a bad guest loop can now retry instead of damaging host backing. It is not a demonstrated cause of the first byte read.

   Exclusive reads go through the regular read callbacks (128-bit reads are two 64-bit reads), so they inherit round 1's page-boundary handling. With UWP fastmem disabled, `EmitExclusiveReadMemory`/`EmitExclusiveWriteMemory` use `ReadAndMark`/`DoExclusiveOperation`, which lock the shared monitor. `Unsafe_IgnoreGlobalMonitor` bypasses the *inline* monitor helpers; it does not remove those callback-path locks. MSVC CAS implementations in `src/common/atomic_ops.h` use Interlocked operations, including compare-exchange-128. The patch does not add a lock or change valid aligned atomic accesses.

4. **The NPDM “heap size” was definitely bogus; the actual virtual layout is plausible.** `src/core/loader/nca.cpp:83` removes the read from offset `0x28`, which lies inside `application_name` (`src/core/file_sys/program_metadata.h:108`). `0x6e6f69` is name bytes, not a heap budget. It was used only to select the IPC pointer buffer. For this log it selected `0x8000`, equal to the retained process default, so the fix should not change this title's heap or IPC-buffer size.

   `code_size=0x315f000` is about **49.37 MiB**, accumulated over page-aligned NSO images including data/BSS and SDK modules, not text size alone (`src/core/loader/deconstructed_rom_directory.cpp:204` and `src/core/loader/nso.cpp:191`). The near-2-GiB code base follows the deliberate 39-bit ASLR policy at `src/core/hle/kernel/k_process.cpp:1226`. Zero system-resource size selects the default resources; it is not intrinsically invalid. The heap region is a reservation of 8 GiB, not a statement that all of it is mapped. `SetHeapSize` and the physical-memory accounting use 64-bit host `size_t`/address arithmetic (`src/core/hle/kernel/k_page_table_base.cpp:2271`, `src/core/hle/kernel/k_process.cpp:863`); no overflow at the supplied sizes was found. No `GetNumPagesOfHeap` helper exists under that name here. Exact compatibility with the retail 1.6 module layout requires the new per-module/NPDM lines; the old log alone cannot authenticate it.

5. **W^X cross-core patch races are lower priority after reading ownership/invalidation.** `src/core/hle/kernel/k_process.cpp:1315` creates one JIT per core and shares only the exclusive monitor. The allocator in `src/dynarmic/src/dynarmic/backend/x64/block_of_code.cpp:85` reserves separate VM allocations; its shared allocator object is stateless. Block emission patches that JIT's own cache. Cross-thread invalidation records ranges under a mutex and requests a halt; `src/dynarmic/src/dynarmic/backend/x64/a64_interface.cpp:311` applies them outside guest execution. Thus the proposed “another core executes the same cache while it is RW” race was not established. VirtualProtect/commit return values remain unchecked in `block_of_code.cpp`; that is a residual host-error-reporting weakness, not evidence of silent guest pointer arithmetic corruption. Cache-size reduction changes eviction/compilation frequency, not guest address width.

The fault capture is implemented at `src/core/memory.cpp:678` and `src/core/memory.cpp:622`. Its atomic one-shot is per Memory instance, across cores. A short thread-local scope is active only inside A64 data callbacks (`src/core/arm/dynarmic/arm_dynarmic_64.cpp:30`); translation/HLE accesses cannot accidentally inherit a running guest context. The hook reads the current ARM interface, not a scheduler's stale saved context. The SVC ring lives on KThread and records entry plus completion around dispatch at `src/core/hle/kernel/physical_core.cpp:156`, reacquiring the current physical core after a blocking call. Raw X0 is not always a Result code (for example, some SVCs return a value); `completed=false` means no return was observed.

For precise PC, `src/dynarmic/src/dynarmic/backend/x64/a64_emit_x64.cpp:122` writes the IR memory operation's location descriptor to JIT PC before the access. Reading ordinary `Jit::GetPC()` without this would not identify the faulting instruction. `src/dynarmic/src/dynarmic/ir/opt_passes.cpp:555` prevents later register writes from deleting stores needed at that callback boundary, while retaining value propagation. The feature is enabled only by the NXBOX_UWP wrapper; other targets default off. It does not halt, replay, remap, or change callback results. It does emit extra stores and can alter timing/cache pressure; a disappearing fault is not proof of a fix. For multi-access instructions, registers reflect the callback boundary, possibly after an earlier sub-access of the same instruction.
