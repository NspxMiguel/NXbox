# Mesa d3d12 GPU wait audit

Audited on 2026-10-10 against pristine Mesa `15acdd7ea2b9dcdd62f26fe86b88280d79efc46b` at
`/tmp/mesa-pin`, copied to a temporary checkout and processed by the **complete** NXbox patch chain.
The original checkout was left unchanged. Eden source baseline: `a281ee8598`. Relevant patch
history, excluding work-note files: `7bb0265cab` (busy-buffer staging), `aaa2b1e200` (texture
barrier), `b69bb535b1` (fence polling), `1a400456ec` (opt-in API ring/journal), and `a281ee8598`
(GPU view reinterpretation).

The strongest remaining avoidable wait was injected by NXbox itself: every ordinary command-list
submission drained the GPU under the screen-wide submit mutex. `glFlush` therefore waited even
though `d3d12_flush` has no explicit finish flag handling. This also serialized shader-worker
contexts with the emulator context. The changes below remove that drain and the GPU-only fake
stream-output drains. CPU-visible completion requirements remain.

## Wait mechanics and policy boundaries

`d3d12_flush_cmdlist_and_wait` first waits/resets every submitted batch, submits the current list,
and waits/resets that batch. `d3d12_resource_wait_idle` uses this full drain when the current batch
conflicts; otherwise it waits only submitted batches referencing the BO. `resource_is_busy` performs
timeout-zero reset checks. `synchronize` skips waits for UNSYNCHRONIZED or writes into previously
invalid ranges, rejects a busy DONTBLOCK map (submitting current work if needed), and otherwise
waits. This is why simply making every WRITE map unsynchronized would corrupt live data.

`d3d12_flush` itself ignores finish-style flags except the NXbox frame counter; actual `glFinish` is
implemented in `st_cb_flush.c:st_finish` as flush + infinite screen-fence finish. `glClientWaitSync`
goes through `src/mesa/main/syncobj.c` and passes its timeout to screen fence finish. GL
`glWaitSync` is a server dependency (no direct Eden renderer call found);
`d3d12_context.cpp:d3d12_wait` flushes and records a **queue-side** Wait. Residency/video queue Wait
calls likewise delay GPU execution, not the CPU. Non-null fence event registration in
`d3d12_create_fence` is asynchronous; the null-event eviction call is blocking.

Both new policies are read once per process; restart for A/B changes. The existing
`NXBOX_SYNC_BATCH=0` still suppresses the diagnostic drain irrespective of the new flag. With async
submission, CPU journal/DRED snapshots cannot prove which in-flight batch caused delayed removal;
use `NXBOX_ASYNC_SUBMIT=0` for precise synchronous attribution. GPU profiling automatically uses
synchronous submission while the existing sync policy is enabled; setting SYNC_BATCH=0 continues to
disable its collection as before.

`NXBOX_D3D12_PERF_WAITS` is collected by `game_session.cpp` as `D3D12_PERF_WAITS`, like VIEW_CAST:
`async_submit`, `submit_drain`, `so_enable`, `so_disable`. Atomic counters are shared across driver
translation units/contexts. Publication covers the first 16 events of each kind and every 64
thereafter. Submit counts record selected submission branches, not measured fence latency; SO counts
record removed wait sites, not proof that the original call would have blocked.

## Validation and console follow-up

Host checks apply the full chain to a copy of the pin, compile the generated post-Execute branch
with C++ mocks, and exercise default async, disabled async, profiler-forced sync, existing
SYNC_BATCH=0, SO flags, counters, failed Signal and device loss. They also assert retained
batch-reuse/readback/query protection and GPU SO compaction before reference release. The existing
full-chain suite checks LF/CRLF inputs and rejects repeat application without source changes. Run
`cd tests/port && python3 -m unittest discover -s . -p "test_*.py"`.

Xbox validation remains necessary: same BotW scene with default flags, ASYNC_SUBMIT=0, and
SO_NO_WAIT=0; compare SAMPLER stacks, STALL categories, D3D12_PERF_WAITS, rendering and device-loss
reports. Run timing comparisons without GPU profiling because it deliberately restores submit waits.
No Xbox binary was built or tested by this audit, and no commit/push was made.
